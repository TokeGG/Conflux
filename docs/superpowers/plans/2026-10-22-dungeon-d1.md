# Dungeon rework D1: generated dark rooms Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A player walks through an endless run of random, dark, cluttered dungeon rooms (crypt, hall, cave), walking through a gate to move on, with the mouse look fixed.

**Architecture:** A pure generator in `shared/` turns `(runSeed, depth, roomIndex)` into a `RoomDef` (pieces, colliders, spawns, lights, look) from data recipes. A new `ENDLESS` run mode plans rooms with it; the sim emits `door_entered` when the player walks into an open gate. The client lights the room with a capped set of flickering lights and skins floors and walls from the texture sets.

**Tech Stack:** TypeScript, `node:test` via `tsx`, Three.js 0.164.1, Vite, Playwright smoke.

**Spec:** `docs/superpowers/specs/2026-10-22-dungeon-crawler-rework-design.md` (milestone D1, sections 3, 5, 6, 8; souls, shops, floors and the other themes are D2 to D4).

## Global Constraints

- `shared/` has no DOM, Three.js or art paths; art by logical id only. Randomness only from the four seeded streams (`map` for generation); never `Math.random()` in `shared/`.
- Three.js stays pinned to 0.164.1. Versions stay below 1.0.
- Every task ends with `npm run bump -- "<plain words>"` only when it changes what a player sees (tasks 1, 7, 8); the final task pushes. Owner and dev tools are never in patch notes.
- Before each push: `npm run typecheck` and `npm test` pass; **push the same commit to `main` as well as `claude/conflux-m0`** (owner's standing rule in `CLAUDE.md`).
- Tests first: each test is seen failing before its code. `npm run wiki` after changing enemies or unlocks data (not expected in D1).
- Unverified licences only warn. Cave kit is Kenney CC0 (`licenses.json` already has the kit line).
- A room is a pure function of `(seed, depth, roomIndex)`; same inputs give byte-identical output.
- Spec deviation, for the owner to confirm: the corridor between rooms is replaced in D1 by walking through a lit gate (the next room loads on contact). A separate corridor room is D2.

## Review Focus

1. A generated room with exits blocked by props or unreachable from the start: every seed must be solvable (task 3 test, 500 seeds per theme).
2. An L-shaped or cut footprint whose walls leave a gap or put an enemy outside the room (task 3).
3. The same seed twice giving different rooms, or two different rooms identical (task 3).
4. Walking into a gate before the room is cleared, or twice in a row: the second `door_entered` must not fire, and nothing advances early (task 5).
5. More lights than the GPU budget, or none near the player: the 8-light cap picks the nearest and the torch always exists (task 6).

## File structure

| File | Responsibility |
|---|---|
| `shared/data/themes.json` | Theme recipes: footprint ranges, piece pools and counts, texture sets, light colours, mob pools. |
| `shared/data/pieces.json` | Bounds of every piece the recipes use (generated from the env index by `scripts/gen-pieces.ts`). |
| `shared/src/gen/footprint.ts` | Cells, L-shape cuts, boundary edges, exit choice. |
| `shared/src/gen/place.ts` | Layered prop placement with clearances; light placement. |
| `shared/src/gen/reach.ts` | Grid walkability and reachability check. |
| `shared/src/gen/generate.ts` | `generateRoom`. |
| `shared/src/run/endless.ts` | `ENDLESS` run mode. |
| `client/src/renderer/roomLights.ts` | Light choice, flicker, player torch. |
| `client/src/renderer/skins.ts` | Texture and tint skins for floors and walls. |

### Task 3: Generator core

**Files:** Create `shared/src/gen/{footprint,place,reach,generate,pieces}.ts`; Test `shared/test/gen.test.ts`.

**Interfaces:**
- Consumes: `pieceBounds` (task 2), `Rng`, `makeStreams`, `genColliders` (existing, `shared/src/room.ts`), `RoomDef`, `ThemeDef` (task 4).
- Produces: `generateRoom(data: GameData, seed: number, depth: number, roomIndex: number, theme?: string): GeneratedRoom` where `GeneratedRoom = { room: RoomDef; theme: string }`; `RoomDef` gains optional `lights: LightDef[]` and `look: { floorTex: string; wallTex: string; tint: string }`; `LightDef = { x; y; z: number; color: string; intensity: number; dist: number }` (types in `shared/src/types.ts`); `isSolvable(room: RoomDef): boolean` from `reach.ts` (4 m grid flood fill with the room's colliders and a 0.5 m player radius).

- [ ] **Step 1: Failing tests** in `gen.test.ts`:
  - `500 seeds per theme are solvable`: `isSolvable(generateRoom(...).room)` for seeds 1..500 and each of crypt, hall, cave.
  - `exits, start and enemy spots are clear`: no collider overlaps a 1.5 m circle at the start, each exit, each enemy spot.
  - `walls are closed`: the boundary of the floor cells is fully covered by wall or gate pieces (every boundary edge has a piece within 0.5 m).
  - `same inputs give identical rooms`: `deepEqual` of two calls; `different seeds differ`: at least 95 of 100 seeds give distinct piece lists.
  - `L-shaped footprints keep every enemy spot on a floor cell`.
  - `piece counts stay in the recipe's range` and `a room has 1 to 3 exits`.
- [ ] **Step 2:** Run `npx tsx --test shared/test/gen.test.ts`; expect FAIL.
- [ ] **Step 3: Implement** per spec 5.1 and 6: footprint on a 4 m grid (4 to 8 by 4 to 8 cells, optional corner cut); walls from `template-wall` and `template-wall-detail-a`, gates (`gate`, `gate-metal-bars`) on 1 to 3 non-corner edges, corner fillers; props in the spec's six layers (structure, floor, set pieces 2 to 5, medium 10 to 20, small 40 to 100, wall decor) via rejection sampling against taken circles; drop a placement when it would break `isSolvable`; enemy spots from the remaining free cells; the start opposite the first exit; lights at braziers, candles and exits. Use the `map` stream fork `gen/${depth}/${roomIndex}`.
